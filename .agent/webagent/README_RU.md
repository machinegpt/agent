# Веб-панель JINX

Панель на React + Express + Vite для наблюдения за работающим когнитивным циклом JINX в реальном
времени: ход стадий, план и оценки по раундам, поток рассуждений агента, трафик IPC/RPC, вывод
терминала, файлы рабочей области и diff рабочего дерева.

Панель — **пассивный наблюдатель**. Она никогда не выполняет инструменты и не управляет циклом: всё
состояние принадлежит Python-агенту, а панель лишь отображает то, что находит на диске.

## 2. Требования и быстрый старт

* **Node.js 18+** и npm.
* Python-агент должен быть запущен отдельно (см. корневой `README.md`), иначе панель покажет только
  состояние простоя.

```bash
cd .agent/webagent
npm install
npm run dev
```

Затем откройте **`http://localhost:3301`**.

Во втором терминале запустите агента из корня репозитория:

```bash
python .agent/jinx.py "описание вашей задачи"
```

## 3. npm-скрипты — все семь

| Скрипт | Команда | Что делает |
| :--- | :--- | :--- |
| `dev` | `tsx server.ts` | Запускает `server.ts` напрямую через `tsx`, с Vite в режиме middleware. Используйте для разработки. |
| `build` | `vite build && esbuild server.ts ...` | Собирает клиентский бандл в `dist/assets/`, затем собирает сервер в `dist/server.cjs` (CJS, `esbuild`). |
| `start` | `node dist/server.cjs` | Отдаёт готовый `dist/`. **Требует `NODE_ENV=production`** — см. §4. |
| `clean` | встроенный `node -e` | Удаляет `dist/` и `server.js`. |
| `lint` | `tsc --noEmit` | Проверка типов. Конфигурации ESLint в проекте нет. |
| `test` | `vitest run` | Однократный запуск набора тестов. |
| `test:watch` | `vitest` | Набор тестов в режиме наблюдения. |

Проверено локально: `npm test` сообщает **5 тестовых файлов, 39 тестов, все проходят** (vitest 4.1.9).

## 4. Порты и ловушка с `NODE_ENV=production`

Выбор порта — одно выражение в `server.ts`:

```ts
const isAiStudio = process.env.AI_STUDIO === "true";
const PORT = isAiStudio ? 3000 : (process.env.PORT ? parseInt(process.env.PORT) : 3301);
```

| Ситуация | Порт |
| :--- | :--- |
| Локальная разработка по умолчанию | `3301` |
| Задан `PORT=<n>` | `<n>` |
| `AI_STUDIO=true` | `3000` — **`PORT` игнорируется** |

**Одного `npm run start` недостаточно, чтобы отдать собранное приложение.** Ветка со статикой
управляется `NODE_ENV`:

```ts
if (process.env.NODE_ENV !== "production") {
  // middleware Vite для разработки
} else {
  // отдача dist/
}
```

`npm run start` такую переменную не задаёт, поэтому сервер стартует в режиме Vite-dev. **При этом
сбой происходит молча**: печатается та же строка `Server running on http://127.0.0.1:3301`, и `GET /`
по-прежнему возвращает `200 OK`, но тело оказывается не собранной dev-оболочкой — в нём есть ссылки на
`/@vite/client`, `/@react-refresh` и `/src/main.tsx`, и нет ни одной ссылки на `assets/index-*.js`.
Запускайте так:

```bash
npm run build
NODE_ENV=production npm run start
```

Обратное тоже верно: в production-режиме каталог `dist/` должен существовать, поэтому `build`
обязателен. Если всё настроено верно, `GET /` возвращает собранный `index.html` со ссылкой на
хэшированный бандл.

### Адрес привязки

Адрес прослушивания не зависит от порта:

```ts
const BIND_HOST = process.env.DASHBOARD_BIND_HOST || (isAiStudio && API_TOKEN ? "0.0.0.0" : "127.0.0.1");
```

По умолчанию только localhost, поэтому не настроенная панель недоступна из сети. При старте сервер
выводит предупреждение, если привязан к нелокальному адресу без заданного `DASHBOARD_API_TOKEN`,
поскольку `/api/live-session` возвращает содержимое файлов из `.agent/`. Обратите внимание: это
предупреждение пишется через `console.warn` в **stderr**, а не в stdout — проверяйте stderr, иначе
вы решите, что оно никогда не срабатывало.

## 5. Переменные окружения

| Переменная | По умолчанию | Действие |
| :--- | :--- | :--- |
| `PORT` | `3301` | Порт прослушивания. Игнорируется при `AI_STUDIO=true`. |
| `AI_STUDIO` | *(не задана)* | `true` принудительно задаёт порт `3000` и делает `0.0.0.0` адресом привязки по умолчанию, **если также задан токен** — AI Studio полагается на перенаправление портов. |
| `DASHBOARD_BIND_HOST` | `127.0.0.1` | Адрес прослушивания. |
| `DASHBOARD_API_TOKEN` | *(пусто)* | Если непусто, два защищённых эндпоинта требуют `Authorization: Bearer <token>`. |
| `NODE_ENV` | *(не задана)* | Должно быть `production`, чтобы отдавать `dist/`; любое другое значение включает middleware Vite для разработки. |
| `DISABLE_HMR` | *(не задана)* | `true` отключает и HMR, и слежение за файлами в `vite.config.ts`, чтобы снизить нагрузку на CPU, пока агент переписывает файлы. |

Файл `.env` в `.agent/webagent/` загружается автоматически через `dotenv`.

## 6. HTTP API

| Метод и путь | Авторизация | Ответ |
| :--- | :--- | :--- |
| `GET /api/auth-check` | нет | `{ "tokenConfigured": boolean }` — сообщает *задан ли* токен, но не его значение. Используется клиентом, чтобы решить, нужно ли запрашивать токен. |
| `GET /api/live-session` | bearer, если задан токен | Полный снимок сессии в виде JSON. |
| `GET /api/live-session/stream` | bearer, если задан токен | SSE, тот же снимок отправляется каждые **2 секунды**, сначала посылается heartbeat `:\n\n` для совместимости с прокси. |

Защищённые маршруты используют `requireAuth`, который пропускает запрос, если токен не настроен, и
иначе сравнивает bearer-токен через `crypto.timingSafeEqual`. При неудаче возвращается `401` с
заголовком `WWW-Authenticate: Bearer`.

Поскольку `EventSource` не умеет задавать произвольные заголовки, клиент автоматически переключает
транспорт: без токена используется SSE; после ввода токена — опрос `fetch` с интервалом 2 секунды.
Активный режим отображается в шапке.

Тела запросов ограничены 10 МБ; слишком большие или некорректные JSON возвращают `413`.

## 7. Как формируются данные сессии

`getLiveSessionData()` находит каталог агента, перебирая `<cwd>/.agent`, `<cwd>/../.agent` и
`<cwd>/..`, и принимает каталог только если он называется `.agent` либо содержит `JINX.yaml`.

* **Файлы** — все файлы верхнего уровня `.agent` размером меньше 1 МБ, кроме скрытых, `node_modules`
  и `dist`, а также все файлы `.py` непосредственно внутри `.agent/src/`.
* **Статус** — определяется из `state.exit_ready` / `state.deadlock` в `JINX.yaml` и уточняется по
  `jinx_run_state.yaml`, если он есть: `waiting_for: llm_generate` при `tool_depth == 0` на раунде 1 —
  это `perceive`, иначе `plan`; `tool_depth > 0` — `verify`; `waiting_for: tool_calls` — `execute`
  или `commit`.
* **План** — по одному шагу на каждую запись `state.scores` с указанием `pass_count`/общего числа
  требований и предыдущего сбоя.
* **Мысли** — текстовые блоки ассистента из `history` в `jinx_run_state.yaml` с вырезанными огороженными
  YAML/JSON, временные метки сдвинуты назад с шагом 15 секунд; если истории ещё нет, используются
  синтезированные записи из истории оценок.
* **Журнал IPC** — блоки `tool_use` как `sent`, блоки `tool_result` как `received`.
* **Терминал** — скрипты `bash_exec` и их результаты, сопоставленные по идентификатору инструмента.
* **Различия** — `git diff`, запускаемый в найденном корне репозитория, с кэшем на 3 секунды,
  таймаутом 5 секунд, ограничением буфера 10 МБ и рекурсивным `fs.watch`, сбрасывающим кэш при любом
  изменении.
* **Идентичность сессии** — `Map` в памяти, ключом служит каталог агента. Первая задача —
  `live-session`; каждая новая задача увеличивает счётчик: `live-session-1`, `live-session-2`, … Указанный
  PID — синтетическое значение в диапазоне 10000–19999, а не реальный идентификатор процесса ОС.

**Оговорка по метрикам:** `promptTokens`, `completionTokens` и `estimatedCost` в рабочем пути жёстко
заданы равными `0`, поскольку у Python-агента нет собственного LLM-клиента и он никогда не видит
расход токенов. Реальны только `hostname`, `os` и синтетический PID.

### Сохранение на клиенте

| Ключ localStorage | Назначение |
| :--- | :--- |
| `jinx_sessions` | Сохранённая история запусков, включая импортированные папки. |
| `jinx_active_tab` | Текущая выбранная вкладка. |
| `jinx_live_poll_active` | Включены ли live-обновления. |
| `jinx_api_token` | Bearer-токен, чтобы не спрашивать его повторно после перезагрузки. |
| `workspace_language` | `en` или `ru`. |

При ответе `401` клиент очищает `jinx_api_token` и показывает ошибку с просьбой предоставить
действительный токен.

## 8. Интерфейс

Пять вкладок: **Summary**, **Thoughts**, **Files**, **Console**, **Diffs**.

* **Summary** — полоса `CognitiveLoop` и `RunSummary`. Цикл отображает **семь** стадий: Perceive,
  Analyze, Plan, Execute, Verify, Commit, Completed, а также состояния `idle` и `error` (ошибка
  окрашивает последнюю стадию в красный). Сетка из 7 колонок на десктопе, вертикальная лента времени
  на мобильных.
* **Thoughts** — поток рассуждений агента с фильтрацией по категории (monologue, question, decision,
  check, system) и по стадии, а также с поиском по тексту.
* **Files** — просмотр содержимого файлов `.agent` с копированием в буфер обмена.
* **Console** — две под-вкладки: вывод терминала и сырой журнал IPC/RPC.
* **Diffs** — по карточке на каждый изменённый файл со счётчиками добавлений и удалений. Diff
  отображается как **единая объединённая таблица**, по одной строке на строку файла, с цветом по
  префиксу `+`/`-`, а не как сравнение в две колонки.

### Локализация

`LanguageContext` содержит ровно два языка, `en` и `ru`, по умолчанию `en`. Локали `zh` в коде нет;
китайский README существует, но сам интерфейс доступен только на английском и русском.

### Известное расхождение в метаданных

`metadata.json` заявляет `"name": "MachineGPT Agent Terminal"` и
`"majorCapabilities": ["MAJOR_CAPABILITY_SERVER_SIDE_GEMINI_API"]`. Зависимости от Gemini в
`package.json` нет, и сервер никогда не обращается к LLM. Название также расходится с
`jinx-dashboard` в `package.json` и упоминаниями `MachineGPT` в `utils.ts`. Это устаревший дескриптор,
а не функциональность рантайма.
